# 代码评审报告 (2026-01-30)

## 1. 评审概述
本次评审基于测试报告 (`test_report.md`) 和核心源代码 (`runtime/`, `feedback/`, `vcs/`)，旨在验证实现与文档的一致性，识别潜在风险并提出改进建议。

## 2. 关键发现与一致性检查

### 2.1 运行时环境 (Runtime)
*   **脚本执行** (`executor.py`):
    *   ✅ **一致性**: 实现了沙箱超时 (`timeout`) 和结果变量检查 (`RESULT_VARIABLE`)，与报告描述一致。
    *   ✅ **错误处理**: 能够区分 `SyntaxError`, `TimeoutError`, `MissingResult`, `InvalidResult`，错误码分层清晰。
    *   ⚠️ **风险**: `exec(code, namespace)` 在同一进程中执行，虽然有超时保护，但共享全局命名空间，且无内存限制，可能被恶意脚本影响。报告中提到的“脚本隔离与资源限制”仍需加强。
    *   ⚠️ **缓存机制**: `pickle` 用于缓存 shape (`_save_current_shape`)。测试报告指出“Pickle缓存失效（严重）”在复杂模型上发生，代码中仅有基础的 `try-except` 保护，未见针对复杂拓扑的特殊处理或降级策略。

*   **几何验证** (`validator.py`):
    *   ✅ **一致性**: 实现了基础 `is_valid` 检查、OCP `BRepCheck_Analyzer`、体积检查和流形检查。
    *   ⚠️ **缺失**: 设计文档中提到的“唯一解检查（欠定义/过定义）”目前主要依赖几何内核的报错，代码层面缺乏针对参数约束的显式检查逻辑。
    *   ⚠️ **依赖**: 强依赖 `OCP`，虽然有 `try-except ImportError` 保护，但如果 OCP 不可用，验证能力会大幅降级。

### 2.2 反馈系统 (Feedback)
*   **渲染器** (`renderer.py`):
    *   ✅ **一致性**: 实现了钢笔画风格（`feature_edges` + `silhouette`），使用了 `pyvista` 的离屏渲染。
    *   ✅ **改进**: 实现了自动相机缩放 (`scale_factor`)，修复了之前的相机位置问题。
    *   ⚠️ **元数据缺失**: 代码仅保存了 PNG 图片，未按设计契约输出包含视图参数的 JSON 元数据文件。这会影响后续的复现和 AI 对视角的理解。
    *   ⚠️ **中间文件**: 使用了 `tempfile` 生成 STL 中间文件，虽然有 `unlink` 清理，但频繁 IO 可能影响性能。直接传递内存对象给 pyvista 会更高效（需验证 pyvista 对 OCP 对象的支持）。

### 2.3 版本控制 (VCS)
*   **仓库管理** (`repository.py`):
    *   ✅ **一致性**: 实现了线性提交历史，`commit` 包含时间戳、消息、度量数据和缩略图。
    *   ✅ **状态检查**: 通过比较 `mtime` 实现了简单的 `status` 检查。
    *   ⚠️ **局限性**: 目前仅硬编码支持 `main.py` 作为脚本路径 (`commit` 方法默认参数)，多文件项目支持不足。
    *   ⚠️ **并发**: 文件读写（JSON/Pickle）未见文件锁机制，如果未来支持并发操作可能会有竞争风险。

## 3. 问题与建议

### 3.1 严重问题 (High Priority)
1.  **Pickle 缓存失效**:
    *   **现象**: 复杂模型无法序列化/反序列化。
    *   **建议**: 放弃 pickle 缓存 shape 对象，改为缓存生成的 STEP 文件（作为中间交换格式），或者在 execute 时直接返回 shape 不依赖磁盘缓存（如果架构允许）。临时方案是捕获 pickle 错误并禁用当次缓存，防止流程中断。

2.  **渲染元数据缺失**:
    *   **现象**: 仅有图片，无相机参数。
    *   **建议**: 在 `render` 方法中，除了 `screenshot`，同时写入同名的 `.json` 文件，记录 `camera_position`, `focal_point`, `view_up`, `scale_factor` 等。

### 3.2 中等问题 (Medium Priority)
3.  **脚本执行隔离**:
    *   **现象**: `exec` 共享进程内存。
    *   **建议**: v1.1 考虑使用 `multiprocessing` 将脚本执行放到独立子进程中，这样可以更安全地强制终止（解决死循环无法响应信号的问题）并清理内存。

4.  **OCP 依赖管理**:
    *   **现象**: 强依赖 OCP 进行高级验证。
    *   **建议**: 在 `validate` 中增加对 OCP 缺失的显式警告（Warning），并在文档中强调推荐安装环境。

### 3.3 优化建议 (Low Priority)
5.  **渲染性能**: 探索直接将 OCP 拓扑转换为 PyVista Mesh 的内存方法，避免 STL 中间文件读写。
6.  **多文件支持**: VCS 模块应支持扫描项目目录下的所有 `.py` 文件，而不仅仅是 `main.py`。

## 3.5 v2 方向下的修正建议（意见稿）

以下建议面向开发期的 v2 方向，作为讨论用的意见稿，不代表已确定的实施方案。

1.  **脚本隔离与可终止性（P0）**:
    *   **原因**: Windows 上当前超时机制为“事后检查”，无法中断 `exec` 中的死循环，导致超时不可控。
    *   **建议**: 将脚本执行迁移到独立子进程/子解释器，超时后强制终止并回传结构化结果（错误/运行日志/工件路径），确保主进程可控、可回收。

2.  **以工件替代形状缓存（P0）**:
    *   **原因**: 复杂 BRep 的 Python Pickle 不稳定，且与 v2 的“模型包 + 工件”理念冲突。
    *   **建议**: 长期缓存统一用 STEP/BREP 等交换工件；运行时仅保留内存对象，不将 shape 作为跨进程/跨运行持久化对象。

3.  **渲染契约补齐（P1）**:
    *   **原因**: 缺少相机位姿与视角元数据会削弱可复现性，也不利于多模态对齐。
    *   **建议**: 每张缩略图旁生成配套 JSON（view 名称、position/focal/up、单位、时间戳、分辨率等），并在 manifest 中建立引用。

4.  **构建可复现性与溯源（P1）**:
    *   **原因**: v2 将产物视为“构建工件”，需要可解释与可重放，否则同一 commit 在不同环境可能生成不同 STEP/缩略图。
    *   **建议**: 记录依赖版本（Python/build123d/OCP/pyvista）、关键配置（单位/容差/超时/渲染参数）到 runlog 与工件元数据中。

5.  **内部 VCS 的身份与摘要（P2）**:
    *   **原因**: commit 若仅靠时间戳生成，难以表达“同源同产物”的关系。
    *   **建议**: 至少记录脚本内容摘要与配置摘要作为 provenance；是否参与 hash 可后续再定。

6.  **Unique Solution 从“报错别名”走向“显式约束”（P2）**:
    *   **原因**: 仅依赖几何内核异常无法覆盖欠定义/过定义的语义检查。
    *   **建议**: 为特征/参数引入可机器读取的 schema/约束声明，作为 validate 的输入之一，逐步让“唯一解检查”具备可解释性。

## 4. 结论
代码实现整体质量较高，核心功能与设计文档和测试报告吻合。主要风险集中在 **数据持久化 (Pickle)** 和 **元数据完整性** 上。建议在 v1.0 发布前修复 Pickle 问题（或提供稳健的 fallback），并补齐渲染元数据输出。
